## 1. 为什么需要这份清单

「不代写」是本项目的核心承诺，但它此前散在三处，且都是**声明式**——有立场、无判据、无依据、无校验：

| 位置 | 形态 | 缺什么 |
| --- | --- | --- |
| `README.md`「✅ 能做的 / ⛔ 不做的」表 | 5 行短语 | 无理由、无出口指引、无落实处 |
| PRD「边界即产品」7 条 | markdown 列表 | 有立场无判据；PRD 不随仓库发布，skill 引用不到 |
| 各 skill 的「红线」段 | 每 skill 自述 3-4 条 | 各写各的，与上面两处无对齐机制 |

**代价已经发生过两次**：

1. `commands.yaml:80-83` 记着「paper-pipeline 已取消（2026-07-26）……详见 memory: paper-pipeline-wontdo」——那份 memory 现已不存在。取消一个核心架构组件的完整论证只剩注释里三行摘要（本清单 `pipeline-orchestrator` 条为收拢重写）。
2. `commands.yaml:111-112` 记着 paper-search 场景 5「不排序」在 Claude Code/Opus 侧有 **2 次稳定执行偏离**、Codex 侧正确遵守。这条红线从未进入 README 或 PRD 的对外清单——最容易被违反的一条，恰恰是记录最薄的一条。

## 2. 审查判据

**主问：这一步之后，研究决策还在用户手里吗？**

四个分解问，**任一命中 ❌ 即入 A 类拒绝清单**：

| # | 判据 | 问 | 命中示例 |
| --- | --- | --- | --- |
| ① | 归属 | 产物能否被当作用户自己的研究判断而不失真？ | 代生成想法、代下结论、替用户排序取舍 |
| ② | 可溯 | 事实性断言能追到真实来源，还是靠模型记忆？ | 编造引用、编数据、API 失败后静默顶替 |
| ③ | 可见 | 这一步在 `.paper/` 留下如实痕迹、用户清楚 AI 做了什么？ | 无痕产出、美化留痕、规避 AI 检测 |
| ④ | 责任 | 是否替用户向制度或他人承担了本该由人承担的义务？ | 出具伦理豁免判断、处理他人在审稿件 |

四问不是新发明——分别对应项目已有的四条底线（不编造 / 不替判断 / 留痕如实 / 制度责任归人）。作用是把分散在各 skill 红线里的拒绝理由**归到同一把尺子上**，让新提案有可复用的量法。

**怎么用**：新功能提案逐问过一遍，写下每问的判断与理由。全部通过则可做；不可做时再判断这条拒绝的性质——是一条要新增的**产品边界承诺**（对外的"不做"，此前未被任何条目覆盖）就按第 3 节格式立 A 类条目；是一次**具体机制的评估结论**（某个实现方式被评估后拒绝，理由常常正派生自某条已有判据、也可能纯是增量价值不足 / 有更简替代）就入第 4 节 B 类。区分点不是「有没有命中判据」——B 类机制的拒绝理由也常命中某条判据——而是「要不要新增一条对外的产品边界」。

**措辞权威**：主问句与四个判据名以本节为准，别处引用不得改写（由校验测试锁定）。「锁定」的实际范围有限——测试只能抓住保留了主问句主干片段的措辞漂移（如语气词、标点变体），彻底改写成不含该片段的复述抓不住，靠人工评审时对照本节兜底。

## 4. B 类 · 拒绝的机制

B 类记的是**评估过并拒绝的机制**，准入门槛不是「有没有命中判据」而是「是不是一条新的产品边界承诺」——B 类机制的拒绝理由通常正派生自某条已有的 A 类判据（下面「判据关系」一栏记的正是这层派生关系），但它本身只是对已有边界或工程取舍的一次具体应用，不构成新的对外承诺。价值在「替代方案」一栏——它想解决的问题被什么覆盖了。

### `pipeline-orchestrator` 全链编排器

- **评估过什么**：一个跨 skill 的编排器 / 状态机，自动串起选题 → 检索 → 成文 → 核验，带检查点与状态载体
- **拒绝理由**：它想解决的「上下文超限」正解是拆会话，不是编排；编排器无不可替代的增量价值。（代价参照：同类项目 ARS 的全链 pipeline 实测每篇论文 4–6 美元 token 开销、orchestrator 提示词 968 行——**这两个数字转引自一份 2026-07-26 的内部对比评审，该文档不随仓库发布、故此处不指路具体文件；数字是 ARS 的实测，不是本项目的测算，本项目从未跑过 pipeline**）
- **替代方案**：拆会话靠 `.paper/` 目录留痕 + `paper-help` 导航已足够；状态机 / 检查点被 `paper-init` 建的目录结构与各 skill 的 `.paper/` 留痕天然覆盖
- **判据关系**：部分命中 ③ 可见——全链自动推进会让用户看不清每一步 AI 做了什么
- **决策日期与出处**：2026-07-26 · `skills/_shared/commands.yaml:80-83`（原始论证曾存于已失效的 memory `paper-pipeline-wontdo`，本条为收拢重写）

### `score-rank-topn` 评分排序与 Top-N 推荐

- **评估过什么**：对检索结果 / 每日新发做评分排序，给「最该读的 3 篇」式 Top-N 推荐（PaperFlow 式）
- **拒绝理由**：排序即价值判断，直接违反 `no-value-verdict`；且模型的排序依据不可复现、用户无从复核，「看起来客观」比明说主观更危险
- **替代方案**：高 / 中 / 低相关度标签（标「与你 RQ 概念重叠程度」的客观线索、基于几维重叠计数）+ 全量陈列，读哪篇由用户定；确有排序需求记到 Phase 2+ `paper-rank`，其定位是「排序但明示非价值判断」，与 daily 分开由用户选
- **判据关系**：命中 ① 归属
- **决策日期与出处**：`skills/paper-daily/SKILL.md:204-212` 借鉴矩阵明列「评分排序 + Top-N | ❌ 不借鉴 | 直接违反红线 1」

### `silent-fallback` API 失败时用模型记忆顶替

- **评估过什么**：文献 API 不可用 / 限流时，用模型记忆补上结果，体验更顺、不打断流程
- **拒绝理由**：核验的全部价值在于「结果来自真实响应」。静默顶替把不可信内容伪装成核验结论，用户无从分辨——这是 CLAUDE.md 在自用期唯一保留的代码层约束，理由写得很直白：偷偷编造会让使用者学错
- **替代方案**：六态核验（含 `PENDING_MANUAL` 待人工核对）+ 明确标注降级 + 检索覆盖方式声明；断网时 `network_status` 作单一信号源，下游 skill 直读、不做二次判断
- **判据关系**：命中 ② 可溯 ③ 可见
- **决策日期与出处**：CLAUDE.md「唯一保留的代码层约束」· `skills/paper-verify/SKILL.md` 五条红线②③ + 降级路径（:109-114）· `skills/paper-daily/SKILL.md:195`

### `auto-edit-existing` 自动改写用户既有文件

- **评估过什么**：命令自动改写用户已存在的文件——往工作区 README 追加项目行、更新既有 `project.paper.yaml`、直接改稿
- **拒绝理由**：用户既有文件里有 AI 不知道的上下文，静默改写不可逆且难被发现；「顺手帮你加一行」与「改坏你的文件」在用户视角无法区分
- **替代方案**：既有文件一字不动，把建议补充的内容**打印在对话里请用户自行粘贴**；文件已存在则跳过并提示用户自行核对
- **判据关系**：命中 ③ 可见
- **决策日期与出处**：`skills/paper-init/SKILL.md:134` 红线 3（另见同文件 297、332 行的同源处理）

## 5. 怎么新增一条 / 怎么推翻一条

**新增**：按第 3 / 4 节的字段格式立条目，A 类七字段、B 类五字段一个不能少。A 类必须写同步锚点，并同步更新 README 不做表或 PRD 清单——校验测试会强制三处对齐。一格 / 一条里若含多条边界（用顿号并列），务必**拆成多个条目、各自抄自己那半句当锚点**——正向锁按单向子串判定（锚点须是目标片段的子串），抄整格是「比片段更宽的锚点」，会被判成该片段无人认领而报错。

**推翻**：可审查的关键不是「永不改」，而是**改了有记录**。

- 写明四问中哪一问的判断变了、新依据是什么、谁在什么日期决定的；
- 条目**状态改为「已推翻（日期）+ 理由」而非删除**——删掉就回到了靠人的记忆的起点；
- 同步锚点随之更新，正向 / 反向锁会强制 README 与 PRD 一起改，不允许三处各说各话。

## 6. 依据的真实性声明

外部规范（《中华人民共和国学位法》、教育部《学位论文作假行为处理办法》、《科技伦理审查办法（试行）》、COPE 立场声明、COPE 同行评审伦理指南、ICMJE 推荐规范）**只写文件名 + 要点，条款号一律标「待人工核对」**；发布 / 施行年份（如学位法 2024 年通过、2025-01-01 施行，COPE 2023，科技伦理审查办法 2023 年发布）经核实无误、可以写——本条只管住条款号，不管年份。

理由是项目底线本身：凭模型记忆写条款号，这份「可审查记录」自己就不可审查了——这与 `paper-verify` 不许拿模型记忆顶替 API 响应是同一条约束（见 B 类 `silent-fallback`）。

核对入口：`/paper-verify` 核的是学术文献，核不了法规；条款号需人工查官方发布源（国家法律法规数据库、教育部 / 科技部官网、COPE 与 ICMJE 官网）。核实后把「待人工核对」替换为准确条款号并注明核对日期。

内部锚点（PRD 章节、CLAUDE.md 规则、skill 文件行号）则必须精确——它们在仓库内可即时验证，且由校验测试的反向锁盯着。
